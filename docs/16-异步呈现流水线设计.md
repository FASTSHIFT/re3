# 16 - 异步呈现流水线设计（去 glFinish，隐藏 GPU 时间）

> 目标平台：Raspberry Pi Zero 2 W（VC4，OpenGL ES 2.0，Mesa 25）。
> 目标：把每帧的 GPU 渲染时间从「CPU 串行等待」变成「与 CPU 下一帧提交并行」，
> 隐藏 `glFinish` 的等待开销。

---

## 1. 背景与现状时序

本项目是**离屏渲染 + 读回推屏**架构（docs/07、docs/08）：surfaceless EGL/GBM
没有默认帧缓冲，主相机渲染到一个 **texture-backed FBO**，然后 CPU 用
`glReadPixels` 读回 RGB565，交给后台 SPI 线程推到 ST7789 屏。

关键代码：
- `vendor/librw/src/gl/gl3device.cpp` `showRaster()`（GBM 分支）：
  `bindFramebuffer(fbo); glFinish();` —— **每帧一次显式全同步**。
- `vendor/librw/src/gl/gl3raster.cpp` `rasterCreateCamera()`：相机 raster 挂一个
  565 颜色纹理 + FBO，配 `rasterCreateZbuffer` 的 DEPTH_COMPONENT24 RBO。
- `src/skel/gbm/gbm.cpp`：`psCameraShowRaster` 里 `RwCameraShowRaster(...,
  rwRASTERFLIPDONTWAIT)`（其内部即 showRaster 的 glFinish），随后 `glReadPixels`
  读回，再 `gSink->present()` 交 SPI（SPI 已是后台双缓冲线程，docs/06）。

**现状是串行的：**

```
帧N:  [CPU 打包 draw calls] → [glFinish 等 GPU] → [glReadPixels] → [present→SPI]
            ~14ms                  3~10ms            ~0.6ms         (后台线程)
```

`glFinish` 期间 CPU 干等 GPU。实测 `gGpuMs`：轻场景 ~3.5ms，重场景可达 ~10ms。
这段等待是纯浪费——CPU 本可同时去打包下一帧。

## 2. 瓶颈定位（perf 实证，见分析记录）

- 主线程 CPU 忙约 77.5%（task-clock 0.775 CPU）。
- CPU 时间约 62% 花在 **draw-call 提交**（libgallium 46% 打包 CL + vc4 内核校验
  CL）。draw call 数 600~700。
- **GPU 占用仅 ~50%**：GPU 在等 CPU 喂命令。GPU 渲染本身（gGpuMs）不是持续瓶颈，
  但 `glFinish` 让它的耗时**串行叠加**进帧时间。

结论：两个正交的优化方向——
1. **降 draw call 数**（攻那 62% CPU 大头，靠 draw distance / 合批）。
2. **本设计：异步化，隐藏 gGpuMs**（把 3~10ms 的 GPU 等待与 CPU 提交并行）。

## 3. 为什么不能简单删掉 glFinish

删掉 `glFinish` 但仍读回**同一帧**的 FBO，`glReadPixels` 会成为**隐式同步点**——
它必须等 GPU 渲完该 FBO 才能读到正确像素，等待只是从 glFinish 挪到 glReadPixels，
没有净收益。

要真正并行，必须**读回上一帧**、让 GPU 去渲下一帧，两者操作**不同的 FBO**。

## 4. 方案对比

### 方案 A：PBO 异步读回（存疑，GLES2 需扩展）
`glReadPixels` 目标设为 Pixel Buffer Object，调用立即返回（GPU 异步 DMA 到 PBO），
下一帧再 `glMapBuffer` 取上一帧结果。
- 优点：连「读回拷贝」都异步。
- 障碍：**GLES2 不含 PBO**，需 `GL_NV_pixel_buffer_object` 扩展。VC4/Mesa 是否
  暴露该扩展**未确认**（当前上下文为 OpenGL ES 2.0）。若无则不可用。

### 方案 B：双 FBO 乒乓 + 去 glFinish + 延迟一帧（推荐，GLES2 必然可行）
准备**两套**相机渲染目标（各自 565 颜色纹理 + FBO + depth RBO），逐帧交替：
- 帧 N：相机渲染到 **FBO_A**（GPU 忙），CPU 同时 `glReadPixels` 读 **FBO_B**
  （帧 N-1 的结果，GPU 早已渲完）→ present(N-1)。
- 帧 N+1：渲染到 FBO_B，读回 FBO_A。交替。
- 因为读的是「已完成」的 FBO，`glReadPixels` 不 stall，**可去掉 glFinish**。
- 优点：不依赖任何扩展，GLES2 原生可行；逻辑直观。
- 代价：**画面延迟一帧（~30ms）**；多一份 FBO+纹理+depth 显存（320×240×2B ≈ 150KB
  颜色 + depth，CMA 余量足够，见 docs/04）。

**采用方案 B。** 若实测确认有 PBO 扩展，可作为方案 B 之上的增量（读回也异步）。

## 5. 目标时序（方案 B）

```
帧序:      N-2        N-1         N
CPU提交:              打包(N-1)   打包(N)
GPU渲染:   渲染(N-2)  渲染(N-1)   渲染(N)      ← 与 CPU 打包(N) 并行
读回+SPI:  present    读回(N-2)   读回(N-1)
                      →SPI(N-2)   →SPI(N-1)
```

帧时从 `CPU + GPU + read + present`（串行）变为 `max(CPU提交, GPU, ...)`。GPU 越重
（重场景 ~10ms）收益越大。

## 6. 实现改动点

1. **双相机 FBO**：在 GBM 分支为相机 raster 分配两套 (color565 tex + fbo)，共享或
   各配一个 depth RBO（depth 不需保留跨帧，可共享一个以省显存——但需确认交替渲染时
   depth 不冲突；保守起见各配一个）。维护 `curFbo` 索引每帧翻转。
   - 位置：`gl3raster.cpp rasterCreateCamera` / 新增管理，或在 `gbm.cpp` 层持有两个
     camera raster 交替。倾向在 skeleton 层（gbm.cpp）管理，少动 librw。
2. **去 glFinish**：`showRaster` GBM 分支移除 `glFinish()`（改为不等待）。
3. **延迟一帧读回**：`gbm.cpp` present 路径改为「发起本帧渲染后，读回上一帧的 FBO
   纹理」。首帧（无 N-1）跳过 present 或推黑帧。
4. **HUD 叠加**：HUD 目前画在读回 buffer 上（`Hud_Draw(gReadback565)`），改为画在
   「被读回的那一帧」对应 buffer 上，保持与画面同步（延迟一帧，无感）。
5. **读回正确性**：读一个已完成 FBO 的纹理，需 `glBindFramebuffer(prevFbo)` +
   `glReadPixels`；确认 VC4 上从非当前渲染目标的 FBO 读回可行（预期可行）。

## 7. 风险

- **时序 bug**：读到未完成/错帧 → 撕裂或错位。必须在模拟器逐帧验证画面正确。
- **首帧冷启动**：N-1 无数据，需跳过或黑帧，避免读到未初始化纹理。
- **深度缓冲**：双 FBO 若共享 depth，交替渲染需保证每帧 clear；VC4 depth 已知有坑
  （docs/04：必须独立 DEPTH_COMPONENT24 RBO），双 FBO 时更要小心。
- **延迟一帧**：输入到显示多 ~30ms 延迟。GTA 手柄操作可接受，但需主观确认。
- **收益不确定**：若某场景 CPU 打包（14ms）远大于 GPU（3ms），并行后帧时仍由 CPU
  决定，收益小。收益上限 = gGpuMs（重场景 ~10ms，值得；轻场景 ~3ms，一般）。

## 8. 验证计划（先模拟器，后 Pi）

1. **模拟器（build-sdl-cn，SDL 窗口）**：实现双 FBO + 去 glFinish + 延迟一帧，
   肉眼确认画面正确、无撕裂/错位/闪烁，HUD 与画面同步，输入延迟可接受。
2. **Pi A/B**：同场景对比开/关异步的帧率，重点看**重场景（gGpuMs 大）**的提升；
   确认无画面异常。
3. 记录数据，若达预期则固化（编译开关，默认 Pi 开）。

## 9. 与已有优化的关系

- 与「降 draw call」正交，可叠加。
- SPI 后台双缓冲（docs/06）已把 SPI 推送异步化；本设计进一步把 **GPU 渲染**也
  异步化，形成 CPU‖GPU‖读回‖SPI 的多级流水线。
- 收益天花板 = 每帧 `gGpuMs`。建议实现前先采几个重场景的 gGpuMs 分布确认量级。
