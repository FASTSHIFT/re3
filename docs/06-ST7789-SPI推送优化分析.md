# 06 - ST7789 SPI 推送优化分析

> 目标：把 re3 的画面通过 SPI 推送到 ST7789 屏（用户态推送，追求接近 SPI/DMA 极限的帧率）。本文档为**独立子任务**，供单独的优化上下文使用。

## 1. 目标与场景

- **屏幕**：ST7789 控制器，SPI 接口，典型分辨率 240×240 / 240×320 / 320×240。
- **方式**：用户态推送（应用层把 framebuffer 通过 SPI 写到屏，不走内核 fbtft/DRM）。
- **性能诉求**：把 SPI 榨到接近 DMA 极限。参考经验：RK3506 上原厂驱动因"动态 malloc + 每次只传 4K"限制到 30fps，改为静态分配 + 单次 64K 大块传输后稳定 60fps。
- **理论帧率**（RGB565，2 字节/像素）：
  - 240×240 = 115KB/帧 → 60MHz(7.5MB/s) 理论 ~65fps
  - 320×240 = 150KB/帧 → 60MHz 理论 ~50fps
  - 差分更新（只推变化像素）可进一步提升。

## 2. 树莓派 SPI 机制（关键约束）

RPI 主控驱动 `spi-bcm2835.c`，三种传输模式按大小自动选：

| 传输大小 | 模式 | 常量 |
|---|---|---|
| < 96 字节 | polling（CPU 忙等） | `BCM2835_SPI_DMA_MIN_LENGTH = 96` |
| ≥ 96 字节且可 DMA | **DMA** | — |
| 其它 | interrupt | — |

**硬限制**：
- **单次传输 ≤ 65535 字节**：`DLEN` 寄存器 16 位，从 BCM2835(Pi1) 到 BCM2711(Pi4) 一直如此。单次 DMA 最多 ~64K。
- **DMA lite channel 限制 32K**：部分 DMA 通道被限制到 32K（内核 commit 明确）。
- **spidev `bufsiz` 默认 4096**：`/dev/spidev` 用户态缓冲默认仅 4KB。**这是用户态推送最主要的软瓶颈**——一帧 150KB 会被拆成 ~37 次 4K ioctl。

**与 RK3506 的差异**：
| 项 | RK3506 原厂 | RPI |
|---|---|---|
| 每次传输分配 | 动态 malloc（瓶颈） | 内核 DMA 用预设 buffer，不 malloc |
| 单次大小 | 4K（瓶颈） | spidev bufsiz=4096（软限，可调）；内核 DMA 单次上限 64K（硬限，DLEN） |
| 优化手段 | 改驱动：静态分配+64K | 调大 bufsiz + 应用层凑大块 + 确保走 DMA |

## 3. 现有参考实现的瓶颈（`ref_lv_gba_emu/port/rpi/st7789.c`）

之前的 ST7789 实现（依赖 wiringPi 的 `wiringPiSPIDataRW`）：

```c
#define DISP_SPI_CLK (60 * 1000000)       // 60MHz
#define DISP_SPI_DATA_MAX_SIZE 4096        // ← 每次传输拆成 4K

static void write_data_buf(...) {
    while (size > DISP_SPI_DATA_MAX_SIZE) {
        DISP_WRITE_DATA_BUF(ptr, DISP_SPI_DATA_MAX_SIZE);  // 4K 一次
        ptr += DISP_SPI_DATA_MAX_SIZE; size -= DISP_SPI_DATA_MAX_SIZE;
    }
    DISP_WRITE_DATA_BUF(ptr, size);
}
```

**瓶颈点**：
1. **4K 拆分**：`DISP_SPI_DATA_MAX_SIZE=4096` 与 spidev 默认 bufsiz 一致。一帧被拆成几十次 ioctl，每次都有系统调用 + 传输建立开销。
2. **wiringPiSPIDataRW 是同步 ioctl**：每次 `SPI_IOC_MESSAGE` 阻塞等待完成，无法流水线/异步。
3. **全帧推送**：`st7789_draw_bitmap` 每次推整帧，无差分更新。
4. **60MHz 时钟**：需确认实际是否稳定（core_freq 漂移问题，见下）。

## 4. 优化方向（供子任务实施）

### 4.1 调大 spidev bufsiz（最直接，不改驱动）

```
# 内核模块参数（/boot/firmware/cmdline.txt 或 modprobe 配置）
spidev.bufsiz=65536
```
把每次 ioctl 从 4K 提到 64K，一帧 150KB 只需 3 次传输（vs 37 次）。**对应 RK3506 的"大块传输"优化，且无需改内核。**

### 4.2 应用层单次凑到接近 64K（DLEN 上限）

- 把 `DISP_SPI_DATA_MAX_SIZE` 从 4096 提到 **32768**（避开 lite channel 32K 限制，最安全）或试 65535。
- 静态分配传输 buffer（避免 RK3506 那种每次 malloc）。

### 4.3 确保走 DMA 而非 polling

- 每次传输 ≥96 字节（整帧推送天然满足）。
- 用 `SPI_IOC_MESSAGE` 且传输足够大，让内核走 DMA 路径。

### 4.4 锁定 core_freq 保证 SPI 速率稳定

SPI 时钟 = `core_freq / 分频`。`core_freq` 默认随负载/温度动态调频，SPI 实际速率会漂。**必须在 `config.txt` 锁定**：
```
core_freq=250
core_freq_min=250
```
否则设 60MHz 实际可能变 48MHz 或波动。

### 4.5 差分更新（进阶）

只推和上一帧不同的区域（脏矩形）。GTA III 画面天空/路面帧间变化小，差分更新可大幅减少 SPI 传输量。参考 `fbcp-ili9341` 的差分 + DMA 策略。

### 4.6 双缓冲 + 异步 DMA（进阶）

用 `/dev/spidev` 的异步接口或直接 mmap DMA，渲染下一帧时后台推当前帧，隐藏 SPI 传输延迟。

## 5.5 基准测试实测结果（2026-08-05，Pi Zero 2 W / bullseye）

测试机：Raspberry Pi Zero 2 W，Raspbian 11 (bullseye)，内核 5.10.92，SPI0（`/dev/spidev0.0`）。
测试程序：`tools/spi_bench/spi_bench.c`（纯 spidev ioctl，半双工写，不驱动 DC/RST，只测总线吞吐）。
基准环境：`dtparam=spi=on` 已启用，**core_freq 未锁定，实测 core clock = 400MHz**。

### 5.5.1 baseline（bufsiz=4096 默认，请求 60MHz，320×240=150KB/帧）

```
chunk=4096 B | ioctls/frame=38 | 3.39 MB/s | 23.1 fps
chunk>4096   | 全部 "Message too long"（内核 bufsiz=4096 硬拦截）
```

### 5.5.2 调大 bufsiz=65536 后（`modprobe spidev bufsiz=65536`）

| chunk | ioctls/帧 | 吞吐 | fps |
|---|---|---|---|
| 4096 | 38 | 3.55 MB/s | 24.2 |
| 8192 | 19 | 3.45 MB/s | 23.5 |
| 16384 | 10 | 3.58 MB/s | 24.5 |
| 32768 | 5 | 3.63 MB/s | 24.8 |
| 65535 | 3 | 3.65 MB/s | 24.9 |

**关键发现 1**：调大 chunk 让 ioctl 从 38 次降到 3 次，但**吞吐几乎不变**（3.39→3.65 MB/s）。
说明在 RPi 上，**ioctl 拆分次数不是主瓶颈**（内核 DMA 本就不 malloc，与 RK3506 原厂"每次 malloc"的情况不同）。
bufsiz 仍需调大（否则 >4K 传输直接失败），但收益主要是"能用大块"，而非吞吐飞跃。

### 5.5.3 频率扫描（chunk=32768，320×240）——揭示真正瓶颈

| 请求 hz | 实际有效时钟 | 吞吐 | fps |
|---|---|---|---|
| 20M | 400/20=20M | 1.48 MB/s | 10.1 |
| 40M | 400/10=40M | 2.92 MB/s | 19.9 |
| 50M | 400/8=50M | 3.64 MB/s | 24.9 |
| **60M** | **400/8=50M（被量化）** | 3.63 MB/s | 24.8 |
| 62.5M | 400/8=50M | 3.63 MB/s | 24.8 |
| 80M | 400/6=66.7M | 4.82 MB/s | 32.9 |
| **100M** | 400/4=100M | **7.10 MB/s** | 48.4 |
| 125M | 400/4=100M | 7.13 MB/s | 48.7 |

**关键发现 2**：SPI 实际时钟 = `core_freq / 偶数分频`，被整数量化。
参考实现设的 **60MHz 实际只跑到 50MHz**（400/8），这才是 baseline 卡在 3.6 MB/s 的真正根因——不是 ioctl 拆分。
要提速必须**请求能被 core_freq 整除的频率**（100MHz→400/4）。

### 5.5.4 目标分辨率 240×240（115KB/帧，bufsiz=65536，chunk=65535）

| 有效时钟 | 吞吐 | fps |
|---|---|---|
| 50M（=请求60M） | 3.66 MB/s | 33.3 |
| **100M** | **7.23 MB/s** | **65.8** ✅ |

**结论**：240×240 @ 100MHz 可达 **65.8 fps**，满足 docs 期望的 60fps 目标。

### 5.5.5 优化优先级（据实测修正）

1. **首要：提高有效 SPI 时钟**（收益最大）。请求 100MHz（需 ST7789 接屏实测能否稳定接收，手册标称 ~62MHz，社区常超频到 ~80-125MHz）。
2. **锁定 core_freq**（`core_freq=400 core_freq_min=400 force_turbo=1`），否则分频漂移导致实际速率波动。当前 core=400MHz，若降频则同样请求会得到更低时钟。
3. **bufsiz 调大到 65536**：必要（否则 >4K 传输失败），但对吞吐本身增益小。
4. **chunk 用 32768**（避开 DMA-lite 32K 限制最安全，与 65535 吞吐等价）。
5. 差分更新 / 双缓冲：进一步提升，见 4.5 / 4.6。

> 注：以上为**总线纯写**吞吐上限。接实屏后需叠加 ST7789 的 GRAM 写入时序、CS/DC 切换开销，实际 fps 会略低，且高频能否稳定取决于屏和排线质量。

## 5.6 端到端 + 内核打点：真正的瓶颈是 CPU governor（2026-08-05）

> 本节是本任务最关键的发现。用"复用参考驱动 st7789.c + wiringPi shim（GPIO 走 pi_gpio 库 + spidev）"做端到端黑白双 buffer 切换测试，并用**内核 SPI tracepoint / function_graph** 逐层打点，推翻了多个基于用户态测量的错误结论。

### 5.6.1 端到端逐层开销分解（100MHz, 320×240, 32K chunk）

用 shim 插桩统计一帧刷屏各类调用耗时：

| 类别 | 次数/帧 | 每帧耗时 | 占比 |
|---|---|---|---|
| GPIO digitalWrite（pi_gpio 库） | 18 | 7.0 us | 0.03% |
| SPI 小 ioctl（set_addr_window） | 5 | 289 us | 1.4% |
| SPI 大数据传输 | 5 | 20618 us | **98.6%** |

**结论**：GPIO 开销（pi_gpio 每次 0.39us）和小 ioctl 加起来仅 1.4%，**不是瓶颈**。问题 100% 在大数据传输。

### 5.6.2 内核 tracepoint：SPI DMA 本身接近满速（97%）

`spi:spi_transfer_start/stop` 打点，测内核里净传输时间：

- 32K 传输：内核 transfer_start→stop = **2.70 ms**；理论(8clk/byte@100M)=2.62ms → **效率 97%**
- 150KB 整帧（内核按 64K DLEN 拆 3 段）：净传输 12.56ms；理论 12.29ms → **效率 97.8%**

即：**SPI 线速率本来就接近满速，不存在"每字节 13 clk 的硬件间隙"**（那是用户态测量的假象，混入了下述 governor 开销）。

### 5.6.3 function_graph：DMA 完成回调落在 CPU idle 上下文

追 `bcm2835_spi_*`，发现 `bcm2835_spi_dma_tx_done` 触发在 **CPU0 `<idle>`** 上下文。SPI DMA 期间 CPU 无负载→进入 idle→`ondemand` governor 降频，DMA 完成回调与下一段传输发起被拖慢。

### 5.6.4 根因锁定：ondemand governor 降频

| 配置（100MHz SPI, 320×240 单大块） | 吞吐 | fps |
|---|---|---|
| **ondemand governor（默认）** | 7.24 MB/s | 49.5 |
| **performance governor** | **11.61 MB/s** | **79.2** ✅ |

切 governor 一个动作，吞吐从 7.24→11.61 MB/s（+60%），与内核 tracepoint 的 97% 效率吻合。

**端到端 e2e（含 GPIO + addr window + 32K 拆分）@ performance = 76.8 fps**，远超 60fps。

### 5.6.5 最终结论（修正 5.5 的判断）

1. **用户的算术正确**：60fps 需 9.216 MB/s = 73.7 Mbit/s，满效率下 ~74MHz 即可。
2. **真正瓶颈是 CPU `ondemand` governor 在 SPI DMA 空闲期降频**，不是 SPI 硬件间隙、不是 GPIO、不是 ioctl 拆分、不是 bufsiz。这些之前的怀疑逐一被内核打点排除。
3. **达标配置**：`performance` governor + SPI 请求 100MHz（受 core_freq=400 偶数分频限制的最低可用档，400/4=100M）→ 端到端 **76.8 fps**，有充足余量。
4. 之前 5.5 节"线效率仅 61%"的结论**作废**——那是 ondemand governor 污染了用户态测量，内核视角实为 97%。

### 5.6.6 落地清单

- [ ] 运行时设 `performance` governor：
  `echo performance | sudo tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor`
  或开机固化（`/etc/rc.local` 或 systemd）。
- [ ] SPI 请求 100MHz（实际接屏需确认 ST7789 能稳定接收，手册标称 ~62MHz）。
- [ ] 锁 core_freq=400 防分频漂移。
- [ ] bufsiz 调大到 ≥65536（避免 >4K 传输失败；对吞吐本身影响小）。
- [ ] chunk 用 32768（与单大块吞吐等价，避开 DMA-lite 32K 限制）。
- [ ] 测试工具见 `tools/spi_bench/`（spi_bench / spi_profile / spi_multi / spi_gap / st7789_e2e + ktrace/kgraph 脚本）。

## 6. re3 侧的对接（本仓库范畴）

re3 渲染出的画面需要交给 SPI 推送层。两条路：
1. **离屏渲染 + 读回 + SPI 推**：re3/librw 渲染到离屏 framebuffer（GLES → glReadPixels 或 EGL），转 RGB565，SPI 推送。注意 `glReadPixels` 在 VC4 上可能慢（读回带宽）。
2. **KMS framebuffer → SPI**：re3 全屏渲染到主 framebuffer，另起进程/线程读 `/dev/fb0` 并 SPI 推（类似 fbcp）。

> 推荐分辨率对齐 SPI 屏（如 240×240），这样 re3 内部就渲染小分辨率，既省 GPU 填充率（见 docs/04）又省 SPI 传输量——**一举两得**。
