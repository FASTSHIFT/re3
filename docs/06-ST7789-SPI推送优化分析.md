# 06 - ST7789 SPI 推送优化分析

> 目标：把 re3 的画面通过 SPI 推送到 ST7789 屏（用户态推送，追求接近 SPI/DMA 极限的帧率）。本文档为**独立子任务**，供单独的优化上下文使用。

## 1. 目标与场景

- **屏幕**：ST7789 控制器，SPI 接口，典型分辨率 240×240 / 240×320 / 320×240。
- **方式**：用户态推送（应用层把 framebuffer 通过 SPI 写到屏，不走内核 fbtft/DRM）。
- **性能诉求**：把 SPI 榨到接近 DMA 极限。参考经验：RK3506 上原厂驱动因"动态 malloc + 每次只传 4K"限制到 30fps，改为静态分配 + 单次 64K 大块传输后稳定 60fps。
- **理论帧率**（RGB565，2 字节/像素）：
  - 240×240 = 115KB/帧 → 60MHz(7.5MB/s) 理论 ~65fps
  - 320×240 = 150KB/帧 → 60MHz 理论 ~50fps
  - 差分更新（只推变化像素）可进一步提升。

## 2. 树莓派 SPI 机制（关键约束）

RPI 主控驱动 `spi-bcm2835.c`，三种传输模式按大小自动选：

| 传输大小 | 模式 | 常量 |
|---|---|---|
| < 96 字节 | polling（CPU 忙等） | `BCM2835_SPI_DMA_MIN_LENGTH = 96` |
| ≥ 96 字节且可 DMA | **DMA** | — |
| 其它 | interrupt | — |

**硬限制**：
- **单次传输 ≤ 65535 字节**：`DLEN` 寄存器 16 位，从 BCM2835(Pi1) 到 BCM2711(Pi4) 一直如此。单次 DMA 最多 ~64K。
- **DMA lite channel 限制 32K**：部分 DMA 通道被限制到 32K（内核 commit 明确）。
- **spidev `bufsiz` 默认 4096**：`/dev/spidev` 用户态缓冲默认仅 4KB。**这是用户态推送最主要的软瓶颈**——一帧 150KB 会被拆成 ~37 次 4K ioctl。

**与 RK3506 的差异**：
| 项 | RK3506 原厂 | RPI |
|---|---|---|
| 每次传输分配 | 动态 malloc（瓶颈） | 内核 DMA 用预设 buffer，不 malloc |
| 单次大小 | 4K（瓶颈） | spidev bufsiz=4096（软限，可调）；内核 DMA 单次上限 64K（硬限，DLEN） |
| 优化手段 | 改驱动：静态分配+64K | 调大 bufsiz + 应用层凑大块 + 确保走 DMA |

## 3. 现有参考实现的瓶颈（`ref_lv_gba_emu/port/rpi/st7789.c`）

之前的 ST7789 实现（依赖 wiringPi 的 `wiringPiSPIDataRW`）：

```c
#define DISP_SPI_CLK (60 * 1000000)       // 60MHz
#define DISP_SPI_DATA_MAX_SIZE 4096        // ← 每次传输拆成 4K

static void write_data_buf(...) {
    while (size > DISP_SPI_DATA_MAX_SIZE) {
        DISP_WRITE_DATA_BUF(ptr, DISP_SPI_DATA_MAX_SIZE);  // 4K 一次
        ptr += DISP_SPI_DATA_MAX_SIZE; size -= DISP_SPI_DATA_MAX_SIZE;
    }
    DISP_WRITE_DATA_BUF(ptr, size);
}
```

**瓶颈点**：
1. **4K 拆分**：`DISP_SPI_DATA_MAX_SIZE=4096` 与 spidev 默认 bufsiz 一致。一帧被拆成几十次 ioctl，每次都有系统调用 + 传输建立开销。
2. **wiringPiSPIDataRW 是同步 ioctl**：每次 `SPI_IOC_MESSAGE` 阻塞等待完成，无法流水线/异步。
3. **全帧推送**：`st7789_draw_bitmap` 每次推整帧，无差分更新。
4. **60MHz 时钟**：需确认实际是否稳定（core_freq 漂移问题，见下）。

## 4. 优化方向（供子任务实施）

### 4.1 调大 spidev bufsiz（最直接，不改驱动）

```
# 内核模块参数（/boot/firmware/cmdline.txt 或 modprobe 配置）
spidev.bufsiz=65536
```
把每次 ioctl 从 4K 提到 64K，一帧 150KB 只需 3 次传输（vs 37 次）。**对应 RK3506 的"大块传输"优化，且无需改内核。**

### 4.2 应用层单次凑到接近 64K（DLEN 上限）

- 把 `DISP_SPI_DATA_MAX_SIZE` 从 4096 提到 **32768**（避开 lite channel 32K 限制，最安全）或试 65535。
- 静态分配传输 buffer（避免 RK3506 那种每次 malloc）。

### 4.3 确保走 DMA 而非 polling

- 每次传输 ≥96 字节（整帧推送天然满足）。
- 用 `SPI_IOC_MESSAGE` 且传输足够大，让内核走 DMA 路径。

### 4.4 锁定 core_freq 保证 SPI 速率稳定

SPI 时钟 = `core_freq / 分频`。`core_freq` 默认随负载/温度动态调频，SPI 实际速率会漂。**必须在 `config.txt` 锁定**：
```
core_freq=250
core_freq_min=250
```
否则设 60MHz 实际可能变 48MHz 或波动。

### 4.5 差分更新（进阶）

只推和上一帧不同的区域（脏矩形）。GTA III 画面天空/路面帧间变化小，差分更新可大幅减少 SPI 传输量。参考 `fbcp-ili9341` 的差分 + DMA 策略。

### 4.6 双缓冲 + 异步 DMA（进阶）

用 `/dev/spidev` 的异步接口或直接 mmap DMA，渲染下一帧时后台推当前帧，隐藏 SPI 传输延迟。

## 6. re3 侧的对接（本仓库范畴）

re3 渲染出的画面需要交给 SPI 推送层。两条路：
1. **离屏渲染 + 读回 + SPI 推**：re3/librw 渲染到离屏 framebuffer（GLES → glReadPixels 或 EGL），转 RGB565，SPI 推送。注意 `glReadPixels` 在 VC4 上可能慢（读回带宽）。
2. **KMS framebuffer → SPI**：re3 全屏渲染到主 framebuffer，另起进程/线程读 `/dev/fb0` 并 SPI 推（类似 fbcp）。

> 推荐分辨率对齐 SPI 屏（如 240×240），这样 re3 内部就渲染小分辨率，既省 GPU 填充率（见 docs/04）又省 SPI 传输量——**一举两得**。
