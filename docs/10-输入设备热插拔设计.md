# 10 - 输入设备热插拔设计（GBM/evdev 输入源）

## 背景

GBM（无窗口）骨架通过 `src/skel/gbm/input_evdev.cpp` 直接读取
`/dev/input/event*`，把键盘、鼠标、手柄注入 re3。相比桌面构建（GLFW/SDL2
自带热插拔），我们没有窗口系统事件泵，需要自己处理运行期设备的插入与拔出：

- 手柄在游戏启动后才连接（USB 或蓝牙）应能被识别。
- 设备拔出（或蓝牙断连）应及时从轮询表移除，避免对死 fd 反复 read。
- 设备在同名节点上重新枚举（如 DualSense 短暂掉线重连，`eventN` 复用）应能自愈。

本文记录热插拔的方案选型与最终设计。

## 业界通用做法

桌面游戏通常不直接操作 evdev，而是依赖库处理这层脏活：

- **SDL2**：插拔以事件形式推送（`SDL_CONTROLLERDEVICEADDED/REMOVED`），主循环
  `SDL_PollEvent` 即可拿到。SDL 在 Linux 上底层用的正是 udev + evdev。
- **GLFW**：`glfwSetJoystickCallback` 注册回调，`GLFW_CONNECTED/DISCONNECTED`。
  re3 的 glfw 骨架（`joysChangeCB`）就是这样。

而这些库的底层，以及不用库的引擎，在 Linux 上的标准机制是
**udev / netlink uevent**：

- 打开 `udev_monitor`（libudev）或直接开
  `socket(AF_NETLINK, SOCK_DGRAM, NETLINK_KOBJECT_UEVENT)`。
- 内核通过 netlink 广播设备增删（`add@ .../input/.../eventN`、`remove@ ...`）。
- **关键性质：内核的 add@ 在 input 设备驱动 probe 完成后才广播**——节点能力位
  （EVIOCGBIT 等）此刻已可查询，不像 inotify 的 IN_CREATE 那样在驱动尚未就绪时
  就触发。

  但要注意一个细节：**内核广播 add@ 的时刻，早于 udev 给新节点应用 ACL / `input`
  组权限**。所以监听方在收到 add@ 后立刻 `open()` 仍可能因权限未就位而失败
  （EACCES）。这不是设备未就绪，而是权限竞态，处理方式见下文“待重试队列”。

## 为什么不用 inotify

初版用 `inotify` 监听 `/dev/input` 的 `IN_CREATE/IN_DELETE`。实测发现：

- `IN_CREATE` 是**文件系统层面**事件——inode 一出现就触发，**早于**内核 input
  驱动 probe 完成、也早于 udev 打好 ACL 权限。结果：`open()`/`EVIOCGBIT` 常在
  CREATE 瞬间失败，设备加不进来（现象：能收到 DELETE 打印 `-eventN`，但对应的
  `+eventN` 没跟上）。
- 早期用“每秒全量 rescan `/dev/input`”兜底掩盖了这个竞态。但 rescan 会 `open()`
  Pi 上的 HDMI 节点（`event0` vc4-hdmi、`event1` HDMI Jack），实测单次
  `open+EVIOCGBIT` 分别高达 ~60ms、~196ms，一次全量扫描 130-256ms，导致渲染循环
  每秒卡顿一次（见本仓提交历史）。去掉 rescan 后竞态暴露。

给 inotify 打“待就绪重试队列”补丁可以 work，但那是在弥补 inotify 比 udev 早触发的
先天缺陷，需要维护重试窗口这类玄学参数，非正道。

## 最终方案：netlink uevent 监听

改用内核 uevent netlink socket，对齐 SDL/udev 的底层机制，一步到位消除竞态，且
**零第三方依赖**（不链 libudev，纯 socket + 文本解析）。

### 机制

1. 初始化：
   - `open()` + 全量扫描一次 `/dev/input`（拾取启动前已连接的设备）。
   - `socket(AF_NETLINK, SOCK_DGRAM, NETLINK_KOBJECT_UEVENT)`，`bind()` 到
     `nl_groups = 1`（内核广播组），设为非阻塞。
   - `SO_RCVBUFFORCE`/`SO_RCVBUF` 提到 1MB。group 1 承载**所有子系统**的 uevent，
     一次 USB 复合设备热插拔会瞬时爆发几十条消息；默认缓冲会溢出，socket 开始
     返回 `ENOBUFS`，若把它当致命错误处理会导致热插拔**永久停摆**（实测踩过）。
     增大缓冲吸收洪峰，`recv` 出错只跳过当帧、下一帧继续读，绝不永久关闭。
2. 每帧（`evdev_poll`）：非阻塞 `recv()` 读 uevent 消息并解析。
   - uevent 是一串以 `\0` 分隔的 `KEY=VALUE`，首行是 `action@devpath`。
   - 关注 `SUBSYSTEM=input` 且 `DEVNAME` 指向 `eventN` 的消息：
     - `add`    → `try_add_device(eventN)`；**若首次 open 失败（EACCES，udev
       ACL 尚未应用）则把该节点加入待重试队列**。
     - `remove` → 从表中移除该节点，并取消其待重试项。
   - 其余（HDMI、mouseN、jsN、by-id 等）忽略。
3. 待重试队列（`sPending`）：`process_pending()` 每帧对队列里的 add@ 节点重试
   `try_add_device`，成功或超出窗口（~1-2s）即出队。这是 netlink 方案唯一需要的
   小重试，且**只针对内核已宣告的具体节点**，不是盲目 rescan `/dev/input`。
4. 死 fd 兜底：每帧轮询各 fd 时，`read` 若返回真正的掉线 errno
   （`ENODEV/EIO/ENXIO/EBADF`）即移除；另每 ~1s 对**已跟踪的** fd 做一次廉价
   `EVIOCGID` 健康检查（只碰已打开的少数 fd，微秒级，绝不 rescan `/dev/input`）。

### 设备分类（不变）

`try_add_device` 打开节点后按能力位分类，顺序为 **gamepad → keyboard → mouse**：

- gamepad：`EV_KEY` 含 `BTN_GAMEPAD` 且 `EV_ABS` 含 `ABS_X/ABS_Y`。先判它，避免
  手柄的触摸板（`EV_REL`）被当鼠标、其运动传感器子节点被误纳。
- keyboard：`EV_KEY` 且常见按键（A/Z/Space/Enter/Up）命中 ≥3。
- mouse：`EV_REL` 含 `REL_X/REL_Y` 且有 `BTN_LEFT`。

### 手柄状态采样（不变）

`capturePad` 用 `EVIOCGKEY`/`EVIOCGABS` 同步读取当前状态，映射到
`PCTempJoyState`（面键、L1/R1、模拟 L2/R2=`ABS_Z/RZ`、双摇杆 0..255→±128 带死区、
方向键 `ABS_HAT0X/Y`）。多输入源共存时，由 `InputSource_CapturePadAll` 统一
`Clear()` 一次，各源 **OR** 写入自己的贡献（GPIO 与手柄可同时工作互不清零）。

### 优点

- add@ 在设备驱动就绪后到达（能力位可查），不像 inotify 那样在半初始化态触发。
- 无周期性 `/dev/input` 全量 rescan，杜绝 HDMI 节点慢 `open` 引发的每秒卡顿。
- 零第三方依赖，与 SDL/udev 底层同款机制。
- 覆盖同名节点重枚举：内核先发 `remove` 再发 `add`，自然走移除+重加。

### 踩坑记录（实测）

1. **inotify 竞态**：IN_CREATE 早于驱动 probe，首次 open/EVIOCGBIT 常失败。
2. **每秒卡顿**：曾用每秒全量 rescan 兜底，但 `open` Pi 的 HDMI 节点极慢
   （event0 ~60ms、event1 ~196ms），一次扫描 130-256ms，卡渲染循环。已删除。
3. **netlink ENOBUFS 永久停摆**：group 1 洪峰撑爆默认缓冲，把 `recv` 出错当致命
   处理导致热插拔从此不再工作。修复：增大 `SO_RCVBUF`，出错只跳过当帧。
4. **udev ACL 竞态**：内核 add@ 早于 udev 应用权限，首次 open 得 EACCES。修复：
   对已宣告节点做短窗口重试（`sPending`）。

### 权限说明

读取 `/dev/input/event*` 需要 `input` 组权限（或 udev ACL）。运行用户加入 `input`
组即可，无需 root。netlink uevent 组 1 的广播对普通用户可读。
